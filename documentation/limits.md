# Limits

- The V1 simulator has no A/B/C rotary axes, no endstop or probe hardware, no laser PWM or spindle model, and M112 does not flush a move that is already running. Reference traces record current behaviour and are pending human review (`approved_by` is empty).
- V1 size is measured for the Smoothieboard (LPC1768). Debug images are linked with an enlarged flash region. The V2 Prime size adapter has been checked against real optimized and debug builds using an isolated GCC 10 dispatcher; the installed dispatcher still needs GCC 10 support. V2 used bytes sum allocated sections, while remaining capacity accounts for gaps through the highest occupied address in each bank. Neither figure measures runtime heap or stack use.
- V2 build inputs now map source paths to `/smoothie/Firmware` and `/smoothie/flashloader`, including filenames embedded by compiler macros. Results identify this as `canonical-file-prefix-v1`. Compare base and head only under the same policy: historical debug measurements embedded longer dispatcher paths and are not comparable with normalized builds. All four V2 base/head optimized/debug builds have passed with this policy through the isolated dispatcher.
- Local builds use a bounded-memory sandbox without a host output mount and return only bounded final bytes to a trusted collector. Complete V1 execution passed four firmware builds and 26 traces. Complete V2 execution passed four firmware builds, four host-simulator builds and all 30 trace comparisons; it was incomplete because three references lacked independent approval; they are now reviewed by a scripted timing model (not a physical measurement), and a full rerun passed on 2026-11-19 (exit 0, warn). Allocated sections matched the established baselines for both profiles. V2 simulator builds consume only Firmware and exclude the separate bootloader subtree. Local size analysis now dispatches the trusted stage through ni-build and runs ELF parsers inside the bounded sandbox. Both profiles matched every established bank and occupied extent in both configurations; malformed ELF input was rejected. Secure GitHub workflow execution remains unverified.
- The experimental Docker execution adapter is unit-tested, including failed cleanup, uncertain creation, bounded capture, build-result validation and propagation through simulator retries/charts. No live Docker test has run: the build VM lacks Docker. A separately provisioned digest-pinned runtime image is required; this adapter does not make the current GitHub workflows safe or verified.
- V2 simulator support is experimental. Multiple motion and module cases have been exercised, but the full V1 scenario inventory remains under review. Milling coverage checks the toolpath and command acceptance; a step trace does not verify spindle output, laser PWM or physical boards.
- The inspected V2 firmware produces out-of-order planner timing boundaries in host simulation for some short-segment, IJK-arc, delta and smooth-junction blocks. The first three references (short segments, IJK arcs, delta) have scripted analytical reviews of per-move timing; one arc block decelerates 17% faster than the configured limit and is recorded as a known anomaly; the smooth-junction trace has an approximate motion review but its flagged planner fields remain unexplained. Matching a trace does not establish correct motion. Physical-board behavior has not been measured.
- The V1 emergency-stop case uses M112. The inspected V2 firmware revision has no M112 handler, and its console source reports unhandled commands as ignored. The V2 host simulator instead stops with an unhandled-command error. A separate V2 case exercises a simulated kill input; none of these checks validates a physical emergency-stop circuit.
- V2 pause asks the host to stop sending commands. In the host simulator, a motion command sent during suspension still ran, and resume moved back to the saved position. The reviewed case records that observed behavior; it does not test a real host or board.
- Historical GitHub tests used pull requests from the same repository. Real fork behavior and the replacement dispatch protocol remain unverified. A retained historical direction-error run concluded success despite its report showing two simulator failures; local lint and archive parsing do not verify corrected GitHub conclusions.
- Untrusted build commands may tamper with the current job's results. The workflow is not yet safe to rely on for fork contributions.
- The AI review gives advice and can be wrong or unavailable.
- Local runs use ni-build; GitHub uses the profile's pinned compiler and build adapter. The V2 dispatcher integration and GitHub workflow verification remain incomplete.

## Simulator reliability

The simulator is deterministic, so a case that differs from its reference is run a second time. If the second run matches the reference, the case counts as passed and the stage says it was flaky (status warn). If the two runs differ from each other, the stage reports a check error, not a failure of the pull request. A crash (signal) or timeout is retried once; a crash that repeats is a failure of the pull request. Each case runs in its own working directory without stdin.

For V2 runs with a coverage inventory, smoothie-sim's per-block planner checker also reports invariant violations as advice. It examines the tested revision and does not establish whether the base has the same findings. Missing checker data makes the check incomplete; matching a stored trace alone does not prove that its timing is correct.

## Suggested fixes

The model writes the suggestions and may return none. For a blocking call the gate adds a removal diff from the pull request's own added lines, so that case never depends on the model. Other kinds of problem (build errors, leaks) depend on the model.
- The step charts draw pulse-level data only when the base firmware's simulator builds and reproduces the stored reference trace itself; if not, the chart shows planner blocks and says "Pulse view unavailable". Pulses over 400 per motor are not drawn in the zoom, which covers about 90 pulses around the first difference. Pulse shifts of 4 ticks (40 µs) or less are not marked.
